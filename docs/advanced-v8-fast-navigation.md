# 上位版Ver.8.0：申告時の画面遷移を安全に削減する検証実装

日付：2026-10-25。対象：`SUUMO-DEV.user.js` のみ（一般版 `main` は変更禁止）。

## 背景
利用者が、一括申告の掲載→入力→確認→完了を繰り返すとPCが重くなると申告。一般版と上位版の同時起動はない。PCのCPU/RAM計測ログは提供されていないため、**ページ全体の読み込みが原因だとは未確定**。ただし現行コードは申告1件ごとに4ページをロードするので改善候補として合理的。

## 採用した方式
正式な申告POSTをXHR等へ変更したり、入力・確認・完了画面を飛ばすのは、サーバー内部仕様・セッション・入力検証が不明で危険なため不採用。

- 最初の掲載画面は従来どおり表示し、`#js-bknToiawaseFr` の実リンクから、`FR400FG001`（入力画面）への直接GETが**同一origin・正しい物件ID付き**で確認できるかを評価する。
- 未対応の場合は次の物件も従来の画面遷移（追加GET無し）。
- 対応している場合、送信が正式に完了した次の物件について、掲載ページのHTMLを裏側で`fetch`（GET／same-origin cookie／最大3.5秒）で取得する。
- `response.ok`、リダイレクト無し、HTML、十分な本文、掲載IDの明示一致、正式な入力画面へのリンクを確認する。
- キューの所有者・掲載URL・index・itemId・履歴entryの保存済み識別が変化していないこと、送信未確認ガードがないこと、次画面の遷移チケットの保存に成功したことを再確認し、`location.assign` で正式入力ページへ移動する。
- いずれか不成立なら、`queuePageTransition("listing")` を経由して従来の掲載ページへ戻る。不明なURLを組み立てたり、POSTを代行することはない。
- タイマーや画面遷移の対象が古くなった場合は一切移動しない。特に、未確認POSTが発生した物件について処理を続けない。
- 直接入力ページへ進む場合でも既存の`acceptPendingPageContext("input")`とitemIdによるページ同定を維持する。

## 想定される効果・限界
- 条件を満たす2件目以降の申告について、**トップレベルの掲載画面再読み込みを各1回省略**。従来の4ページ表示が3ページになり得る。ただしネットワーク上の掲載ページGETは残る。
- 個別に掲載URLを取得しているため、総通信数が必ず減るわけではない。CSSや広告等の追加アセット処理と画面描画の削減が狙い。
- 実際のSUUMOリンクがJavaScript制御、相対的なフォーム状態、個別IDを含まないURL、またはリダイレクト必須の場合は安全上**最適化されない**。その場合負荷改善もない。
- 取得失敗時は約3.5秒以内に従来表示へ戻す設計なので、その物件は従来より遅くなる場合がある。
- 実サイトで成功率・平均時間・CPU使用量を計測して効果が乏しければ撤回すること。

## 実施した検査
- 本体のJavaScript構文検査：合格。
- 追加ヘルパーの模擬20条件：20合格、0失敗（正常・不正ID・他origin・JavaScript URL・POST以前のガード・HTMLエラー・stale非同期・チケット保存失敗など）。
- テストスクリプト：`tests/fast-report-navigation.cjs`。
- **未検証**：Ver.8.0本体による既存58件のChromium回帰テスト、実Tampermonkey、実SUUMOのリンク形式、実PCの負荷・所要時間、実送信。いずれも合格と表現しない。

## 公開判定
**保留。** `dev`（現状7.54.10）と `main`（一般版8.0）を更新しない。手動テスト時は既存上位版をバックアップし、Tampermonkeyで上位版だけ有効にする。実送信は禁止。

検証時はChromeタスクマネージャー（Shift+Esc）でSUUMOタブのCPU・メモリを比較し、Chrome Consoleで`軽量遷移：掲載画面の表示を省略`のログを確認する。ログが一度も出ない場合は効果が発動していない可能性が高い。対象の掲載ID・物件プロフィール・確認画面の一致、画面履歴戻り、送信結果不明ガード、再試行・掲載終了・最終結果画面の動作を確認する。
